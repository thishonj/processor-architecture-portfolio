# Self-review checklist (use before applying; paste your repo link to Claude for a real review)

## Honesty
- [ ] Every project has **Status**, **Limitations**, and "what I did *not* do"
- [ ] No tool or skill listed that I could not explain in an interview
- [ ] Tutorial/course work is labelled as such; code adapted from others is credited

## Reproducibility
- [ ] A stranger can run `make` (or one command) from a clean clone
- [ ] Expected output is in the README and was copied from a real run
- [ ] Tool versions noted; CI is green

## Technical depth (what hiring managers look for)
- [ ] RTL: at least one module you can explain line by line (decode, ALU, hazard unit)
- [ ] Verification: self-checking tests, a failing case you caught, a bug log
- [ ] You can answer: *What is a load-use hazard? Why does forwarding not fully fix it? What does `volatile` do? Why does `sizeof(arr)` differ in a function?*
- [ ] Results include numbers (cycles, CPI, coverage) with the method stated

## Gaps typical for this goal (add over time)
Caches, branch prediction, AXI/AMBA basics, CDC/reset handling, formal/SVA, UVM, synthesis (Yosys/Vivado) and timing reports, scripting (Python/Tcl), code review/PR habits.

## Presentation
- [ ] Pinned repo, short profile README, clean commit messages, no build artefacts committed
- [ ] German CV (Lebenslauf) / English CV links the repo and says exactly which projects are done
